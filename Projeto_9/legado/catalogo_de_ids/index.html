Padrão de nomenclatura proposto

O nome da pasta ajuda a definir o ID inicialmente, mas depois o ID é estável mesmo se o arquivo for movido. A classificação descreve escopo e reutilização. As rotas React e Flutter são independentes.

Exemplo: um menu reutilizado por todas as telas do advogado

Definição compartilhada: ui.advogado.menu.principal

Tela advogado.home:
  tela.componentes.instanciasRefs["screen.drawer"] = "ui.advogado.menu.principal"

Tela advogado.atendimentos.lista:
  tela.componentes.instanciasRefs["screen.drawer"] = "ui.advogado.menu.principal"
Atenção: os 23 usos atuais de component.drawer.professional.v1 apresentam 23 estruturas distintas. O ID unificado acima é uma intenção de arquitetura, não uma equivalência já comprovada. Precisaremos separar diferenças de conteúdo/seleção ativa da estrutura-base do menu.

Diferença entre as três identidades

Tela: advogado.home · Definição do componente: ui.advogado.menu.principal · Instância local: screen.drawer. Um mesmo componente pode ter diversas instâncias; a instância não cria outra definição global.

Sequência segura de aprovação

1. Revisar telas e componentes na lista. 2. Aprovar IDs das telas. 3. Agrupar componentes por identidade, comparando estruturas. 4. Identificar componentes compartilhados parametrizáveis. 5. Exportar o mapeamento aprovado. 6. Só depois atualizar referências e testar o visualizador.

Reutilização e conflitos de identidade

Repetir o ID não comprova que a estrutura é igual. O levantamento compara a estrutura declarada (HTML/CSS), sem alterar arquivos.

Uso offline. As decisões editadas podem ser exportadas e reimportadas; nenhuma alteração é aplicada ao arquivo das 110 telas sem uma etapa posterior de migração controlada.
